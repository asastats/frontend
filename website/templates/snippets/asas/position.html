{% load static %} {% load core_extras %} {% comment %} One position: a single row in an asset's breakdown. This is the atom the address page is built from. A balance, an LP stake, a deposit, a borrow -- and, where the engine can decompose it, the panel listing what the figure is made of. Rows and cards are the same markup, and this template says nothing about which one applies. Placement comes from `data-layout-position` on ``; rows is what you get with no attribute at all. **The presentation must never be rendered in here.** `cache_page` on `AddressView` is a view decorator, so it runs inside the middleware: `Vary: Cookie` is added by SessionMiddleware *after* `learn_cache_key` has recorded what to key on, and the entry is therefore shared between signed-in readers. A modifier class written here would hand the first reader's layout to everybody who follows. `core/tests/test_address_layout.py` demonstrates that, and asserts this component stays presentation-free. The reader's layout is resolved by `utils.layouts.layout_for_user` and reaches the page off the cache -- the way `_swap_entry.html` does. Source order is presentation-neutral: summary first, then breakdown, with the areas deciding where each lands. The old markup put the breakdown first and pulled it back with `order-1`/`order-2`, which meant a screen reader and a keyboard met the parts before the whole, and a second layout could not be added without a second copy of the markup. Required context: prog one item from asaitem.programs (dict with keys program, value, amount, distribution, proxy, linked, pid) asset the parent asaitem.asset dict price the parent asaitem.price (ALGO per 1 unit of asset) pricealgo account.total.pricealgo (used by the ALGO Balance row) forloop_counter parent loop's forloop.counter (for unique distid IDs) `data-pid` is the position's stable identity, from `api.position_id`. It survives a refresh where neither the value nor the row's place in the list does, and it is what pinning, deep links and the saved layout key on. Where the payload cannot tell two positions apart, `data-pid-ambiguous` says so rather than letting a caller trust a name that means both of them. `data-amount` is the tiebreaker for exactly those rows -- see `pins.js`. It is deliberately *not* part of the pid: hashing it in would change the id whenever the amount changed, which is the one thing the id exists to survive. Amount rather than value because it moves only when the reader actually stakes or unstakes, while value moves with the price on every load.
